# 가상 머신 디스크 풀 장애 복구 보고서

> 원본: 개인 학습 노트(Notion)에서 옮겨 정리. 스크린샷은 생략했습니다.

> 발생 일시: 2026-04-08

관련 실습: Wazuh SIEM 구축 및 Hydra 무차별 대입 공격(Brute Force) 테스트

### 🚨 1. 장애 현상 (Symptom)

- 에러 메시지: Errno 28: 장치에 남은 공간이 없음
- 장애 영향:
  - DNF 패키지 매니저 작동 중단 (metadata_lock.pid 생성 불가).
  - 로그 기록 및 서비스 재시작 불가.
  - 가상 머신 스냅샷 생성 및 정상 종료 실패.

### 🔍 2. 원인 분석 (Root Cause Analysis)

- 보안 로그의 폭발적 증가: Hydra를 이용한 SSH 무차별 대입 공격 실습 중, /var/log/secure 파일에 수만 건의 접속 실패 기록이 쌓임.
- Wazuh 에이전트 부하: 실시간 로그 수집 및 분석 과정에서 /var/ossec/logs/ossec.log 파일 크기가 급격히 팽창.
- 스토리지 임계치: 실습용 VM에 할당된 20GB 남짓한 공간이 보안 실습 중 발생하는 대량의 데이터(Big Data)를 견디지 못함.

### 🛠️ 3. 해결 과정 (Resolution)

#### STEP 1. 디스크 점검

터미널에서 현재 사용량을 확인하여 / (루트) 파티션이 100%임을 식별했습니다.

Bash

df -h

#### STEP 2. 긴급 용량 확보 (파일 내용 비우기)

파일 자체를 삭제(rm)하면 프로세스가 파일을 점유하고 있어 용량이 즉시 반환되지 않을 수 있습니다. 따라서 파일의 크기만 0으로 만드는 방식을 사용했습니다.

Bash

\# 1. SSH 접속 실패 로그 비우기 (가장 큰 원인)

sudo truncate -s 0 /var/log/secure

\# 2. 시스템 일반 로그 비우기

sudo truncate -s 0 /var/log/messages

\# 3. Wazuh 탐지 로그 비우기

sudo truncate -s 0 /var/ossec/logs/ossec.log

#### STEP 3. 캐시 및 임시 파일 정리

용량이 확보된 후 패키지 매니저의 찌꺼기를 정리했습니다.

Bash

sudo dnf clean all

### 💡 4. 향후 재발 방지 대책 (Prevention)

- Logrotate 설정 확인: 로그 파일이 일정 크기를 넘으면 자동으로 압축/삭제되도록 설정 최적화.
- 디스크 모니터링 습관: 실습 전후로 df -h 명령어를 사용하여 잔여 용량을 상시 확인.
- 로그 수준 조정: 공격 실습 시에는 불필요한 디버그 로그가 남지 않도록 Wazuh 및 시스템 로그 레벨 조정.

### 🎓 5. 습득한 직무 역량

1. 인프라 가용성 관리: 시스템 장애 시 로그 분석을 통해 근본 원인을 파악하고 즉각적인 복구 시나리오를 실행함.
1. 리눅스 커널/파일 시스템 이해: 파일 삭제와 truncate 방식의 차이점을 이해하고 실무에 적용함.
1. 보안 운영 실무: 보안 공격(Hydra)이 시스템 가용성에 미치는 부작용(Side Effect)을 경험하며 균형 잡힌 보안 운영의 중요성을 체감함.
